# School Affairs assistant and account data — Issue #90

School Affairs at `/school-affairs` is an independent stu.best workspace. A verified Google account receives its own rows in the client Supabase project. The first account data read initializes a sample program, two sample courses, a practice grade and a sample task. Notices and catalog records also carry provenance. These are **not official university enrollments, grades, fees or announcements**. The site does not collect a university password or read an official SIS. Site tasks and requests persist in the stu.best database, but requests are not sent to the university.

The personal dashboard shows courses, timetable, practice grades, fees, notices, tasks and requests. The verified `luxart0317@gmail.com` Google account receives the site admin role on first School Affairs data access. The admin view lists site accounts/requests, resolves requests, and publishes site notices. Neither this role nor these records grant Nexus permissions. Google identity is checked against Supabase Auth on every private API request. Database RLS enforces account isolation; the functions use the caller JWT and publishable key, not a service-role bypass. The only writing tool exposed to the chat proposes a task, completion, request or admin notice; a separate explicit click executes it through `affairs_execute_action` and writes `affairs_agent_audit`.

Private questions call `/api/affairs-assistant`. The server retrieves only the caller's School Affairs snapshot and sends that snapshot to the configured OpenAI model with `store:false`. It does not pass Nexus data. Responses name the sample boundary and show account grounding. If the model is unavailable, deterministic answers cover the common personal fields and simple task requests still produce a reviewable proposal. Public school questions use the separate research endpoint without a personal JWT or private history. Private account questions do not accept image attachments. The chat records are held only in page memory and clear when the School Affairs account changes.

The schema supports future verified imports through `source_mode`, but no official integration is configured. A Google account alone does not establish university enrollment or identity. The current data model has profiles, terms, programs, courses, sections, students, enrollments, grades, attendance, charges, announcements, tasks, requests and an action audit. Its scope is a functional site workspace, not a complete university ERP. An authorized institutional source, mapping, consent and validation would be required before displaying real student records.
