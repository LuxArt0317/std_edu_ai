The first full browser run exposed seven failures. Some assertions were stale after recent route, embedded-chat and conversation changes; investigation also confirmed user-facing defects. Subsequent 50/51 runs exposed an owner-menu defect, an environmental disk-full failure, and a real chat-history race. Focused owner, support and deliberately delayed history tests pass after their respective corrections. The final complete run is recorded below.

The production connected-assistant acceptance check also found that a question about “my app class” was classified as public. The public lookup could not see the account's class notice, although the authorized record existed. The singular-class classifier is corrected and covered by a source-level regression. The post-deployment live rerun passed all ten checks, including the exact private notice answer and fixture cleanup.

## Defects and repairs

| Severity | Reproduced behavior | Repair and regression |
| --- | --- | --- |
| P2 | Switching the owner from knowledge management to the full workspace left the account menu open. Its modal layer hid the navigation from keyboard and screen-reader access. | Control and close the menu before switching workspaces; the owner role E2E now requires the menu to disappear before traversing navigation. |
| P2 | Knowledge document rows extended outside a 390 px viewport and could overlap status badges. | Allow rows, titles and badges to wrap within their container; mobile service E2E checks viewport width and title/status separation. |
| P2 | Nexus sign-in had no discoverable path to public student registration. | Link `/signup` from `/signin`; browser test checks both routes. |
| P2 | When a returning user sent a message before the selected conversation's history finished loading, the stale history response could replace the new message on screen. | Keep sending unavailable until that thread's history resolves, show a loading state, and render only messages belonging to the selected thread. A deterministic browser test holds the history request, checks the send gate, then checks the old and new messages before and after reload. |
| P2 | “My app class” did not match the personal-question gate, so the authenticated Nexus assistant searched public sources and missed an authorized class notice. | Classify singular and plural class references as personal before any public lookup; the source test checks the exact reported question and the live connected-assistant suite validates the account-specific notice. |
| P2, prevention | CI did not exercise the copied direct school pages that had previously regressed into the app loading shell. | Run the existing public mirror/navigation/assistant browser suite against a local production preview on every code change. |
| Test maintenance | Browser assertions assumed the former parent-page chat, legacy `/crm` destination and an empty assistant thread. | Assert against the embedded chat surface, current owner route and latest message; preserve privacy, source and focus checks. |

## Limits that QA cannot claim away

- **Institutional records:** School Affairs and DTM personal data are clearly marked client-owned samples. Real university SIS and Moodle records require institution-approved integrations and identity mapping; this remains in [#94](https://github.com/LuxArt0317/std_edu_ai/issues/94) and [#93](https://github.com/LuxArt0317/std_edu_ai/issues/93). A Google sign-in is not evidence of access to official academic records.
- **Public email:** Student registration mechanics pass, but ordinary public confirmation delivery needs a client mail provider, tracked in [#75](https://github.com/LuxArt0317/std_edu_ai/issues/75).
- **Account holder:** The actual Lux Google OAuth callback and external account consent must be completed by the account holder, tracked in [#83](https://github.com/LuxArt0317/std_edu_ai/issues/83).
- **Copied school content:** Captured entrance and service pages are checked; deeper archives, source availability and third-party protected systems remain in [#84](https://github.com/LuxArt0317/std_edu_ai/issues/84). A local copy must not be presented as an official university service.
- **Research and operations:** Source ownership, approved corpus, human accessibility and physical-route review, consented participants, independent evaluation and institutional signoff remain in [#63](https://github.com/LuxArt0317/std_edu_ai/issues/63), [#65](https://github.com/LuxArt0317/std_edu_ai/issues/65), [#67](https://github.com/LuxArt0317/std_edu_ai/issues/67), [#69](https://github.com/LuxArt0317/std_edu_ai/issues/69) and [#71](https://github.com/LuxArt0317/std_edu_ai/issues/71). Automated tests are software evidence, not human or school approval.
- **Lint debt:** The 71 warnings predate this change and do not fail the configured gate. React purity/effect warnings merit a separate focused cleanup; broad mechanical changes during this release would add regression risk.

## Final verification and release

The corrected application bundle is live on stu.best: `/`, `/signin`, `/signup`, `/app`, `/school-affairs/login`, `/dtm` and the student entrance return HTTP 200. The post-deployment connected assistant passed ten public, anonymous and signed-in checks, including the previously failing class notice. A first GitHub quality run failed only because the stale-bundle recovery test expected a sign-in form in a build without Supabase credentials. The application correctly rendered its explicit missing-configuration page. The assertion now accepts either booted route state, still requires the stale-entry refresh and removal of the boot shell, and passes against the compiled local preview. The GitHub quality rerun remains before #96 can close.
